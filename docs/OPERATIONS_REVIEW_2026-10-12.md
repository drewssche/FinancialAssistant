## Telegram бот

### Подтверждённая причина прошлых падений

В сохранённом журнале 6420 исключений `IndexError`, совпадающих с `RestartCount=6420`. Первый сбой — 25 сентября 20:17:15, последний — 27 сентября 15:04:43. Текущий процесс работает с 27 сентября. Проверенный traceback ведёт в `handle_message` в `scripts/run_telegram_admin_bot.py`: обращение к `[0]` после `split()` пустого текста. Локальная изолированная проверка воспроизводит ошибку; SHA-256 скрипта совпадает с файлом в контейнере.

### Почему событие возможно без переписки

Бот запрашивает `message` и `callback_query`, чтобы поддерживать `/start`, административные кнопки и подтверждение планов. Telegram `Message` включает нетекстовые и служебные события. Например, `write_access_allowed` может возникнуть при предоставлении боту права писать после запуска Web App; изменения настроек чата тоже могут быть служебными сообщениями. От пользователя не обязательно требуется отправлять текст. Конкретный вид исторического события не записан и сейчас не установлен.

Ответы на собственные `sendMessage`/`sendPhoto` не передаются приложением в `handle_message`. При нажатии inline-кнопки исходное сообщение бота находится внутри callback и проходит через другой обработчик. Подтверждённый traceback относится к верхнеуровневому входящему `message`, а не к callback. Доказательств чтения собственных исходящих сообщений как причины сбоя нет.

Проверка `getMe`/`getWebhookInfo`: токен работает, webhook отсутствует, ожидающих событий на момент проверки нет, `allowed_updates=['message', 'callback_query']`; чтение всех сообщений групп, inline mode и business mode не включены. `can_join_groups=true` означает возможность добавления, а не наличие конкретных групп. Дополнительный `getUpdates` диагностикой не запускался, чтобы не конкурировать с работающим polling.

При падении offset в памяти теряется; неподтверждённое событие может прийти снова после перезапуска. Все сбои нельзя приписать одному сообщению без его ID. Причина прекращения потока ошибок 27 сентября неизвестна; дефект остаётся в коде.

Источники: [Telegram Message](https://core.telegram.org/bots/api#message), [получение событий](https://core.telegram.org/bots/api#getupdates).

### Приоритетное исправление в плане

- Безопасный разбор текста; явное пропускание нетекстовых/служебных сообщений, если для них нет функции продукта. Поддержку фото чеков проектировать отдельно от этого исправления.
- Изоляция исключений отдельного события, различение неподдерживаемого ввода и ошибки важного действия; ограниченные повторы и идемпотентность подтверждения планов.
- Минимальная диагностика: тип события, технический update ID, тип чата и ошибка без текста, токенов и личных данных. Логи позволят определить реальный источник при повторении.
- Регрессии на отсутствие текста, пробелы, служебное событие, `/start`, callback и следующее корректное событие после сбоя.
- Контроль прогресса worker и прироста рестартов. Текущий `Up` не заменяет успешный polling и доставку.

## Сбер

Текущий код обращается к `https://developer.sber-bank.by/api/rates/v1/currencyExchange?exchangeType=Cash`. Внутри контейнера этот hostname не разрешается. Серверный DNS и Cloudflare для A, Google для AAAA возвращают `NOERROR` без адресных записей, с SOA зоны. Это отсутствие адреса, а не доказанный NXDOMAIN и не ошибка разбора JSON. DNS Telegram и Яндекса на том же сервере работает.

Основной `www.sber-bank.by` имеет адрес, но прямое соединение с VPS было сброшено. Через веб-инструмент доступны официальный сайт и [страница наличных курсов](https://www.sber-bank.by/page/currency-exchange-cash); числовые данные и замена API через эту проверку не установлены. Наличие сайта не означает доступность старого API с VPS.

Банк публиковал [плановые ограничения СБОЛ 11–12 октября](https://www.sber-bank.by/new/tekhnicheskie-raboty-sbol-11-12-oktyabrya). Они не объясняют автоматически сбои этого API, присутствующие в журнале уже 27 сентября. Связь с внешними событиями не установлена.

Рекомендации для отдельного этапа:

1. Проверить действующий официальный источник именно наличных курсов, формат buy/sell, масштаб валюты и привязку к отделению; заменить адаптер только после проверки с VPS. Не подменять курсы Сбера курсами другого банка или карточными курсами без явного выбора.
2. Сохранить последнюю успешную цену/курс с датой и существующей отметкой устаревания. Сбой не должен обнулять курс или менять исторические валютные снимки операций.
3. Для длительно недоступного источника увеличить интервалы попыток, например 15 → 30 → 60 минут с ограничением, и возвращать обычный интервал после успеха. Логировать переход состояния и периодическую сводку вместо одинакового сообщения при каждой попытке.
4. В диагностике различать DNS, TCP/TLS, HTTP, формат ответа и пустой результат без записи секретов. Для фонового обновления предпочтительно общее состояние попыток, поскольку текущий словарь throttling локален процессу.

Адрес API и расписание работающего приложения не менялись.

## Яндекс Диск и резервные копии

Таймер запускается ежедневно в 04:15 по Минску. Последний успешный лог — 10 октября, объект `financialassistant-20261010T011515Z.dump.enc`. 11 октября загрузка исчерпала три попытки с HTTP 500; 12 октября — с HTTP 410. Старый путь systemd `/root/projects/financial-assistant` разрешается в актуальный checkout `/root/FinancialAssistant`; скрипты совпадают, ошибка не вызвана этим путём.

Повторная проверка дала:

- Квота аккаунта читается успешно, свободного места достаточно. Это подтверждает работу авторизации для этого запроса, но не всего файлового API.
- Метаданные корня, каталога бэкапов и объекта последнего успешного запуска возвращают HTTP 410.
- Прямой запрос официального `/v1/disk/resources` с существующим токеном, без rclone, тоже возвращает `410 GoneError`.
- Установлен `rclone v1.60.1-DEV`. Его обновление стоит запланировать, но одна только версия клиента не объясняет воспроизведённый прямой HTTP-ответ.

Нельзя по этим ответам утверждать, что файлы удалены, токен окончательно отозван или диск переполнен. Сохранность и восстанавливаемость последнего объекта сейчас не проверены. Ручная повторная загрузка, удаление, смена токена и восстановление БД не выполнялись.

В текущем `backup_postgres.sh` временный дамп и зашифрованная копия удаляются exit-trap даже при неуспешной отправке. Неотправленная копия не остаётся в очереди на следующий запуск. Успешная загрузка и последующая очистка по retention также пока не имеют отдельных статусов.

Рекомендации для отдельного этапа:

1. Проверить тот же каталог через обычный интерфейс Диска; если файловый API продолжит возвращать 410, подготовить обращение в поддержку с временем и кодом ошибки без токена. Сообщение в поддержку сейчас не отправлялось.
2. Сохранять зашифрованные неотправленные копии в ограниченном локальном каталоге повторной отправки. Незашифрованный временный дамп по-прежнему удалять; задать лимит места и срока хранения. Локальная копия помогает пережить сбой отправки, но не заменяет копию вне VPS.
3. Разделить статусы создания, шифрования, загрузки, проверки удалённого объекта и очистки старых копий. Ошибка retention не должна скрывать успешную загрузку, а сообщение об успехе загрузки не должно означать проверенное восстановление.
4. Повторять временные сетевые/5xx ошибки с паузами; 410 показывать как отдельную недоступность ресурса, без бесконечных частых повторов. Добавить сигнал о возрасте последней подтверждённой внешней копии.
5. Рассмотреть резервное внешнее хранилище или временную защищённую выгрузку на отдельный носитель. Назначение выбрать явно; существующие файлы автоматически не переносить.
6. После возвращения доступа проверить восстановление конкретной копии. Текущий скрипт создаёт временную БД в существующем PostgreSQL; для полного релизного прогона предпочтителен отдельный экземпляр с проверкой миграции и ключевых связей/сумм. Рабочая БД не должна быть целью восстановления.
